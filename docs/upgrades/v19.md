# Upgrade to Umbraco 19

From `18.0.0` to `19.0.0-rc1`.
Branch `v19/dev` (renamed from `release/19.0.0` on 12-11-2026), cut from `origin/main` at `7d4dea1`.

**Targets CMS release:** `19.0.0-rc1`. Its GitHub release is still a draft on 12-11-2026, so
there's no tag yet: source is `release/19.0` at `b158b78`. This is a pre-release, so the
package ships as `19.0.0-beta`, following Automate core's naming.

## Decisions

- 12-11-2026: target CMS `19.0.0-rc1`, not beta1: Licenses 19.0.0-beta is gone from MyGet.
- 12-11-2026: port to `ITreeServiceConnector` on `main` first, raising main's Deploy floor to
  18.2.0 (Rick).
- 12-11-2026: `version.json` moves to `19.0.0-beta` in the bump task.
- 12-11-2026: the v19 work lives on a long-lived line, `v19/dev` (Rick). It started as
  `release/19.0.0` and was renamed before any push: a `release/*` push publishes to MyGet,
  and nothing on the line should publish until a pre-release is cut. Each beta or rc is cut
  from `v19/dev` as `release/YYYY.MM.N` (shared monthly counter) and merged back.
  `azure-pipelines.yml` needs `v19/dev` in its triggers so pushes build (markers task).
- 12-11-2026: **split the types like Commerce.Deploy does** (Rick): automations are transfer
  (content); workspaces and connections are disk (settings). Every existing site already has
  `.uda` files for all four types, so disk keeps the settings-like ones where they are.
  Checked: Deploy 19 builds each partial-restore tree level from the parent's connector
  without checking its set (`CurrentEnvironment.GetTreeItems.cs:21-27`, "mixed trees … keep
  working"), so transfer automations under disk workspaces can still be browsed.
- 12-11-2026: **workspace groups are transfer, like automations** (Rick: "effectively the same
  as a content folder"). A workspace group is a folder of automations inside a workspace
  (`AutomateWorkspaceGroupArtifact`). The CMS registers its folders with their items
  (document blueprint and element containers are transfer, `ConfigureDeployEntityTypesOptions.cs:37,70`),
  and Forms folders follow forms. A disk folder created on live would never reach git, so a
  transfer automation inside it could never be restored elsewhere.
- To check in the Deploy port: whether queuing an automation for transfer also brings its
  transfer-type folder dependency. If not, editors queue the folder (with descendants) instead.

## Breaking changes for consumers

- .NET 11, CMS 19, Deploy 19 and Automate 19 are required.
- Automations and workspace groups (automation folders) are transfer only: they no longer write
  `.uda` files, and Deploy 19 ignores their existing `.uda` files on import (it reads and writes
  only registered disk types, #1171 decision 9). Before upgrading, get automations and folders
  in sync across environments. Afterwards, delete their `.uda` files from
  `umbraco/Deploy/Revision` and move them with Queue for transfer or Restore.
- Workspaces and connections are disk only: they no longer show Queue for transfer, Tree
  restore or Partial restore.
- `DeployAutomateComponent` (public) is removed; `Tree/UmbracoAutomateTreeHelper` (internal) too.
- `AddToQueueAction`, `DeployContentAction` and `TriggerRestoreAction` gain a constructor taking
  `IOptionsMonitor<DeployEntityTypesOptions>`; the old constructors stay, `[Obsolete]` for removal
  in v21.
